# AI 持续知识管理

通过专业访谈理解用户的真实知识工作，生成一套自包含的文件型知识体系，并用真实任务启动检索、增量沉淀、影响分析和联动维护。建设完成后，日常工作由项目中的规则、索引、知识关系和用户资料共同支撑。

## 产品边界

- 交付物是用户可读、可编辑的目录、Markdown 规则、索引、关系和必要配置，不建设独立应用或常驻服务。
- 只读取当前任务、目标目录和用户明确授权的来源；不读取无关项目、记忆、旧对话或主目录内容。
- 默认不联网补充资料，不建设爬虫、自动采集、向量检索、RAG、独立知识图谱或企业协作系统。
- 不保存密钥、凭证或无必要的隐私信息，不直接转储完整聊天记录，不永久删除唯一原件。
- 文件权限沿用宿主环境；业务归属、关键关系、跨文档修改、结构变化和删除由用户最终决定。
- 规则和索引应短、准、无重复；用户知识内容不受篇幅限制。

## 统一工作流

### 1. 识别目标与范围

确认用户想长期完成的工作、目标目录、可读取范围和禁止范围。读取 [需求发现与体系设计](references/discovery-and-design.md)，通过开放式追问理解代表性任务、知识对象、关键关系、增量信息、典型变化、检索路径和确认边界。访谈过程中维护知识对象账本；用户明确说出的代表性对象不得在后续总结中无说明消失。

用户已经说明或材料能够确认的信息不得重复询问。每轮只追问一个最影响体系设计的问题；不得用职业模板或示例答案引导用户。

### 2. 按需理解已有资料

目标目录或授权来源包含资料时，读取 [已有资料处理](references/existing-materials.md)。先用 `scripts/runtime_tool.py inventory` 做轻量盘点，再按结构判断和代表性任务需要逐步阅读。空白目录跳过盘点，但仍完成必要访谈。

### 3. 展示体系方案

写入前展示项目目标、知识对象、一级分区、关键关系、状态与来源策略、新信息入口、变化传播方式、未确认假设和实际文件影响，同时展示“用户表达或授权资料 → 知识对象 → 管理方式 → 实际落点”的覆盖映射。被合并、仅作元数据或索引、保留在外部的对象必须说明理由。只有用户确认知识职责、覆盖映射、关系、维护边界及有风险的文件操作后才可写入。

### 4. 生成知识体系

读取 [知识体系运行契约](references/knowledge-system-contract.md)，生成最小必要结构、根与分区 `AGENTS.md`、根与分区 `index.md`、待处理与历史机制、知识关系和轻量运行清单。结构必须来自已确认的真实任务，不得套用固定职业目录，不得生成示例业务数据或占位内容。

读取 [日常知识维护](references/ongoing-maintenance.md)，把查询、对话增量、冲突处理和结构演进规则写入合适层级。通用规则放在根层，分区规则只保留该分区特有内容。

### 5. 建立变化维护机制

读取 [变化影响与联动维护](references/change-impact.md)，把影响分析触发条件、关系传播边界、影响清单、确认门、执行顺序、历史保留和一致性检查写入项目规则。

### 6. 完成首次验证

读取 [首次验证与完成门](references/validation.md)。使用用户的真实任务或经确认的冻结任务，依次验证设计保真、代表性检索、长期增量、临时信息不沉淀、变化影响分析、确认后联动修改和独立一致性检查。

生成验证记录与 `.knowledge-system.json`，运行：

```text
python3 scripts/runtime_tool.py diagnose --project <项目绝对路径> --pretty
```

诊断零错误只是必要条件，不能代替业务验证。

## 运行中的已有体系

目标目录已有 `.knowledge-system.json` 时，先运行 `diagnose` 并读取根入口、目标分区和必要材料。保留用户维护过的规则、索引和业务内容；确定性问题可在当前授权范围内修复，业务归属、关系、状态或流程冲突必须先说明影响并确认。不得为了统一格式批量改写历史资料。

## 完成条件

只有知识职责、知识对象覆盖映射和关键关系已确认、七项首次验证全部通过、影响清单与实际修改一致、当前知识无已知关键冲突、来源与历史可追溯且 `diagnose` 零错误时，才可标记完成。

无法判断的内容进入待处理；阻断问题、未确认假设、失败项和未执行范围必须如实报告。只完成目录、规则或静态检查不得宣布知识体系已可持续运行。
