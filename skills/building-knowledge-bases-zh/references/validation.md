# 首次验证与完成门

## 验证目标

生成目录、规则和索引不等于知识体系可持续运行。必须使用用户的真实任务，或经用户确认的冻结任务，完成以下七项验证：

1. `design_traceability`：把访谈或授权资料中的明确知识对象逐项映射到实际管理落点，经用户确认；
2. `retrieval`：跨必要知识对象完成一次代表性检索，并给出来源路径；
3. `durable_increment`：将一条有长期价值的新信息沉淀到正确位置并建立必要关系；
4. `temporary_input`：确认一条临时指令没有进入长期知识库；
5. `change_impact`：对一项关键变化给出有关系依据的影响清单；
6. `linked_update`：在用户确认范围后完成联动修改，无越权文件；
7. `consistency`：独立复核当前内容、索引、来源、历史和替代关系的一致性。

只搜索文件名、只检查目录存在或只让原执行者自我确认都不算通过。

## 验证记录

将结果写为 JSON。每个阶段必须包含结果、简短结论和项目内真实证据路径：

```json
{
  "result": "passed",
  "stages": {
    "retrieval": {
      "result": "passed",
      "summary": "已从来源与当前判断完成检索",
      "evidence": ["资料/来源.md", "判断/当前结论.md"]
    }
  }
}
```

`design_traceability` 还必须包含：

```json
{
  "confirmed_by_user": true,
  "knowledge_objects": [
    {
      "name": "需求文档",
      "source": "用户访谈",
      "management": "section",
      "target": "04_需求文档"
    }
  ]
}
```

`management` 允许 `section`、`document_type`、`metadata`、`index`、`external_reference` 或 `merged`。使用后四种方式时必须提供 `rationale`，解释为何不独立管理。映射记录不证明语义一定正确，但能阻止用户已明确对象在交付中无说明消失。

实际文件必须补齐全部七个阶段。任一阶段失败、证据路径不存在、确认门被绕过、明确对象没有管理落点或仍有关键当前结论冲突时，总结果不得标为 `passed`。

## 确定性检查

写入运行清单后执行：

```text
python3 scripts/runtime_tool.py diagnose --project <项目绝对路径> --pretty
```

诊断检查必要入口、分区规则、生成文件、验证阶段、项目内 Markdown 链接和规则指纹。错误必须修复；规则变化警告表示用户可能维护过规则，应理解并安全合并，不得直接覆盖。

确定性检查不判断业务关系或对象提取是否正确，也不能代替七项真实任务验证。

## 完成条件

只有同时满足以下条件才可将运行清单设为 `complete`：

- 用户已确认知识职责、关键关系和维护边界；
- 七项首次验证全部通过并有真实证据；
- 用户明确的代表性知识对象覆盖率为 100%，合并或降级项有理由并已确认；
- 影响分析与实际修改范围一致；
- 当前有效内容没有已知关键冲突；
- 来源、历史和替代关系可追溯；
- `diagnose` 返回零错误；
- 未完成与不确定事项已如实报告。

阻断问题存在时使用 `building` 或 `incomplete`，并说明下一步，不得以静态结构通过代替业务完成。
